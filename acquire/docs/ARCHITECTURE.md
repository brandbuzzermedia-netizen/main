# Architecture

## 1. Existing codebase (audit, 26 Oct 2026)

The repository `brandbuzzermedia-netizen/main` held two things before this work:

| Path | What it is | Relationship to Acquire |
|------|------------|-------------------------|
| repo root (`*.html`, `styles.css`, `tools/build.py`) | Get Bee Seen agency marketing site: static, generated by a Python script, no dependencies | Unrelated. Untouched. |
| `finance-os/` | GBS's internal receivables app: Next.js 16, React 19, Supabase (Postgres, Auth, RLS), Zod, Vitest, SQL tests in CI | Unrelated domain, but a proven stack and set of conventions. Acquire copies its patterns, not its code paths. |

There was no existing real estate, CRM or outreach code. Acquire lives in `acquire/` as a
separate project, with its own `package.json`, migrations, CI workflow and Vercel project. It
does not import from `finance-os/`.

Patterns reused from Finance OS:
- `auth.ts` context as the data access entry point;
- tenant-keyed RLS with `app.*` helper functions, and the anon lockdown;
- the audit trigger;
- the SQL test harness (`scripts/test-db.sh` plus a Supabase shim, so the tests run on plain Postgres);
- the CSV parser;
- the CSV import wizard (preview first, then commit);
- the UI primitives.

## 2. System shape

A **modular monolith**: one Next.js app and one Postgres database. Long-running work runs in background jobs
(phase 5). No microservices until a concrete need appears.

```
Browser ── Next.js (App Router, server components + server actions)
              │  proxy.ts: refreshes session, gates every non-public route
              │  lib/auth.ts: user → membership → active org → role → permissions
              │
              ├── Supabase Postgres (RLS on every table; anon has no grants)
              │     • tenant data, consent, suppression, audit, plans/usage
              │     • security-definer functions only where RLS can't express the rule
              │
              ├── (phase 4+) Provider adapters: email, SMS, AI model, voice, calendar, GHL
              │     each behind an interface in src/integrations/<area>/, server-only
              │
              └── (phase 5+) Job runner: durable queue in Postgres, signed cron/webhook entry points
```

### Layers in `src/`

| Folder | Rule |
|--------|------|
| `domain/` | Pure TypeScript with no I/O: eligibility rules, normalisation, import planning, schemas, money, dates. Everything here is unit-tested. |
| `lib/` | Server-only plumbing: Supabase clients, auth context, permissions, query builders. |
| `integrations/` | Provider adapters (phase 4+). Each one has an interface, a real implementation and a test double. |
| `app/` | Routes. Pages read through `getContext()`. Mutations are server actions that start with `requirePermission()`. |
| `components/` | Presentational UI only. |

### Where each rule is enforced

| Concern | Enforced in | Why there |
|---------|-------------|-----------|
| Tenant isolation, role access | Postgres RLS (+ UI hides what roles can't do) | Holds even if an app bug forgets a filter |
| Plan limits (contacts, seats) | Database triggers/functions | Server-side, can't be bypassed from the browser |
| Duplicate leads | Unique indexes on normalised email / E.164 phone | Race-safe |
| Consent history immutability | Revoked UPDATE/DELETE + trigger | Evidence must not change |
| Suppression → opted-out stage | Trigger | Every code path, including imports |
| Timeline for create / stage / owner changes | Trigger | Can't be skipped |
| Contact eligibility | `domain/eligibility.ts` (pure, versioned) | Rules need tests, explanations and versions; they will be evaluated before every send |
| Input validation | Zod in server actions, then DB checks | Two layers |

## 3. Data model (implemented: phases 2–3)

```
markets ─┐
plans ───┼─ subscriptions ── organizations ── organization_settings
roles ───┘                    │   │
                              │   └─ memberships ── users ── auth.users
platform_admins ── users      │
                              ├─ pipeline_stages ─┐
                              ├─ lead_sources ────┼── leads ──┬─ lead_activities
                              │                   │           ├─ consent_records (append-only)
                              ├─ suppression_entries (by value; survives lead deletion)
                              ├─ lead_imports      (per-row results)
                              ├─ saved_views
                              ├─ usage_records     (idempotent on provider event id)
                              └─ audit_logs        (trigger-written, redacted on erasure)
```

Key decisions:
- **Dedupe keys.** `email_normalized` (a generated column, `lower(trim(email))`) and `phone_e164` are
  each unique per organization. The same person may exist in two organizations.
- **Statuses are data.** `pipeline_stages` are per organization, renamable and reorderable. Each has a
  `category` (`new`, `working`, `qualified`, `won`, `lost`, `opted_out`). Reports count categories, so
  renaming a stage never breaks a metric. `new` and `opted_out` are system stages.
- **Consent.** One row per event (granted or withdrawn) per channel, with a basis, source, evidence URL,
  capture time and optional expiry. The newest row is the current state (view `lead_consent_latest`).
- **Suppression** is keyed by normalised value and an optional channel (`NULLS NOT DISTINCT`
  uniqueness). An all-channel opt-out moves matching leads to *Opted out*.
- **Erasure** (`erase_lead`):
  - deletes the lead and cascades its history;
  - redacts its audit rows;
  - keeps a suppression entry by default, so the person is not re-imported and contacted again.
- **Money** is stored as bigint minor units plus an ISO currency. Countries use ISO alpha-2 codes,
  time zones use IANA names, and timestamps are UTC.

## 4. Security model

- **Authentication.** Supabase Auth (magic link or password). `proxy.ts` validates the JWT on every
  request with `getClaims()`.
- **Authorization.** RLS on every table, keyed on membership role. Roles:
  - `agency_admin`: everything, including team, settings, erasure and the audit log;
  - `campaign_manager`: all leads and configuration;
  - `sales_rep`: only leads they own; they can record opt-outs and consent but not lift suppressions;
  - `read_only`: reads only.
- **Platform admins** are a separate table. They can list organizations and suspend them through
  `admin_*` functions, but RLS gives them **no** access to tenant leads.
- **Service role** is used only in `settings/actions.ts`, to find or invite a user, and only after
  the action has checked `manageTeam`. The membership itself is written as the caller, so RLS and
  seat limits apply.
- **Anon** holds no grants on anything, now or in later migrations (default privileges are revoked).
- **CSV:**
  - imports are re-parsed on the server at commit time, so a client-sent plan is never trusted;
  - imports are size- and row-limited;
  - exports neutralise spreadsheet formulas.
- **PostgREST filters** built from user input are escaped or quoted. Filter values from the URL are
  validated against allowlists (`lib/leads.ts parseFilters`).
- **Security headers:** `X-Frame-Options: DENY`, `nosniff`, a referrer policy and a permissions policy.

## 5. AI architecture (phase 4+, designed now)

The design uses bounded tasks rather than one general agent. Each task has a typed input, a
JSON-schema output validated with Zod, an explicit tool list, a usage budget, and a run record
(model, prompt version, tokens, cost, latency).

| Task | Can read | Can do | Cannot do |
|------|----------|--------|-----------|
| Lead research summary | The lead record, activity, and provider data the tenant licensed | Write a summary note | Browse the web or invent facts |
| Qualification extractor | Conversation transcript | Propose structured answers, a score and evidence quotes | Change the stage without passing a deterministic rule or a human review |
| Outreach drafter | Lead, template, verified property data | Draft text | Send. Drafts go through approval or a pre-approved template path. |
| Voice qualification agent | Lead context and its script | Ask the configured questions, disclose that it is AI, hand off | Call anyone the eligibility engine has not approved; promise prices or availability |
| Follow-up recommender | Timeline and stage | Suggest the next action | Schedule anything itself |
| CRM assistant | Records | Prepare an update for confirmation | Write to an external CRM without the sync layer |
| Campaign analyst | Aggregated metrics only | Explain them and suggest experiments | See personal data |

Deterministic code, never the model, decides permissions, eligibility, booking confirmation, billing
and stage transitions. Lead messages and imported text are treated as untrusted data:
- they are passed in delimited fields, never concatenated into instructions;
- tools are allowlisted per task;
- outputs are schema-checked, and anything off-schema is rejected.

The default model is Claude through a provider interface, so the model can be configured per task.
