# GBS Engagement Engine — Architecture

An internal Get Bee Seen platform for managing AI-assisted, human-approved social
engagement across many clients from one dashboard. It is built multi-tenant from
the first migration: every client-owned row carries `organization_id` and
`client_id`, Postgres Row Level Security decides what each user can see, and
composite foreign keys make it impossible to link one client's records to
another's.

## 1. What was in the repository

The repository (`brandbuzzermedia-netizen/main`) is the GBS marketing website:
six static HTML pages generated by `tools/build.py`, a Next.js site for a client
under `clients/t3-media-corp/`, and a standalone vanilla-JS tool,
`meta-ads-calculator/`.

| Question | Finding |
| --- | --- |
| Framework | None at the root (static HTML). Next.js 14 in one client site. |
| Database | None. |
| Authentication | None. |
| Components / design system | `styles.css` + `styleguide.html` — GBS brand tokens (cream `#fff2dc`, yellow `#ffb933`, green `#196144`, ink `#191816`). |
| API routes | None. |
| Environment variables | None. |

Nothing existing could host a multi-tenant app, and the repo convention is
"each tool is self-contained in its own directory". So the engine lives in
`engagement-engine/` with its own stack, dependencies, README and tests, and
**no existing file was rewritten or removed**. It reuses the GBS brand tokens.

## 2. Stack

| Layer | Choice | Why |
| --- | --- | --- |
| Web app | Next.js 16 (App Router), React 19, TypeScript | Server components and server actions keep every API call and secret on the server. Server actions have built-in Origin/Host CSRF checks. |
| Styling | Tailwind CSS 4 with GBS brand tokens | Fast, consistent, responsive. |
| Database | PostgreSQL 15+ (Supabase-compatible) | RLS, composite FKs, triggers, `SKIP LOCKED` job queue. |
| DB driver | `pg` (node-postgres) | Lets the app switch to a non-privileged role per transaction so RLS is enforced on **every** request query. Works on Supabase (pooler in session mode) or any Postgres. |
| Auth | First-party email + password (scrypt), DB-backed sessions, `HttpOnly` `Secure` `SameSite=Lax` cookies | No external dependency, and a `users` table the RLS policies can reason about. Swappable for SSO later (see §9). |
| AI | Anthropic Claude via `@anthropic-ai/sdk`, structured outputs (Zod) | Comment generation and post analysis. Default model `claude-opus-5-5`, configurable per organisation. |
| Embeddings | Pluggable: Voyage AI (`VOYAGE_API_KEY`) or a built-in local hashed n-gram embedder | Semantic duplicate detection without leaking text to any service when no key is configured. |
| Background work | Postgres-backed queue + `npm run worker` (long-running) or `/api/cron/*` (serverless cron) | No extra infrastructure. |

## 3. Tenancy model

```
organizations (GBS)                       ← white-label root, one per agency
 └── clients                              ← the isolation boundary
      ├── client_users  (owner | member)  ← client portal logins
      ├── account_managers                ← GBS staff assigned to this client
      ├── brand_profiles, brand_documents
      ├── audience_segments, audience_keywords, target_profiles
      ├── social_accounts, oauth_tokens
      ├── campaigns (+ campaign_segments, campaign_target_profiles)
      ├── posts, engagement_opportunities
      ├── comment_generations, comments, comment_edits, comment_approvals
      ├── publishing_jobs, publishing_results
      ├── engagement_metrics, usage_events, usage_limits, daily_reports
      └── notifications, audit_logs
```

`users` belong to an organisation and carry a **platform role**:

| `platform_role` | Who | Reach |
| --- | --- | --- |
| `super_admin` | GBS super admin | Every client in their organisation. |
| `account_manager` | GBS account manager | Only clients listed in `account_managers` for them. |
| `client_user` | Client owner / team member | Only clients listed in `client_users` for them (normally one). Role per client: `owner` or `member`, with configurable `can_approve` and `can_edit` flags. |

## 4. How client data isolation works

Isolation is enforced in **four independent layers**, so a bug in one does not
leak data.

### Layer 1 — Database: Row Level Security

* Every tenant table has `organization_id` and `client_id` and has RLS enabled.
* Request queries run inside a transaction that does
  `SELECT set_config('app.user_id', $1, true); SET LOCAL ROLE gbs_app;`.
  `gbs_app` is a `NOLOGIN` role with **no** `BYPASSRLS`, so every `SELECT`,
  `INSERT`, `UPDATE` and `DELETE` is filtered by policy.
* Policies call `SECURITY DEFINER` helpers in the `app` schema:
  `app.can_access_client(client_id)`, `app.can_manage_client(client_id)`,
  `app.can_approve_gbs(client_id)`, `app.can_approve_client(client_id)`,
  `app.can_edit_comments(client_id)`.
* A client user therefore gets **zero rows** for another client — not an error
  page, an empty result — including in the client list, so other client names
  are never visible.
* Secrets are outside RLS entirely: `gbs_app` has **no privileges** on
  `oauth_tokens`, `oauth_states`, `sessions` or `rate_limits`, and only
  column-level `SELECT` on `users` (no `password_hash`).

### Layer 2 — Database: composite foreign keys

Every parent table has `UNIQUE (id, client_id)`; every child references the
pair: `FOREIGN KEY (campaign_id, client_id) REFERENCES campaigns (id, client_id)`.
A comment for Client B physically cannot point at Client A's campaign, account,
post or opportunity — Postgres rejects the insert. Likewise
`FOREIGN KEY (client_id, organization_id) REFERENCES clients (id, organization_id)`
pins every row to the right organisation.

### Layer 3 — Application: scoped services

* Pages under `/clients/[clientId]/…` call `requireClientAccess(clientId)`, which
  checks access (and RLS re-checks).
* Every service function takes `clientId` and filters on it explicitly, even
  though RLS would filter anyway.
* Background jobs (which run as the privileged service connection) are always
  driven by a single job row and use **only** that row's `client_id`.

### Layer 4 — AI context isolation

`loadClientAiContext(db, { clientId, campaignId })` is the **only** way context is
assembled for a model call. It:

1. Loads the brand profile, brand documents, audience segments, campaign and
   recent approved/edited comments with `WHERE client_id = $1`.
2. Verifies the campaign belongs to that client.
3. Asserts every loaded record's `client_id` equals the requested one
   (`assertSingleClient`) and throws `ContextIsolationError` otherwise.
4. Returns an object stamped with `clientId` + `campaignId`; the generator
   refuses a post whose `client_id` differs.

Every model request carries `client_id` and `campaign_id` (in request metadata
and in `comment_generations`), and nothing is shared between clients: no global
few-shot examples, no cross-client caches, no fine-tuning. Duplicate detection
compares a comment only with **the same client's** history.

## 5. Engagement pipeline

```
DISCOVERED ─► ANALYZED ─► COMMENT GENERATED ─► QUALITY CHECK ─► PENDING APPROVAL
                                                                   │
                                     ┌─────────────────────────────┴───────────┐
                                     ▼                                         ▼
                                APPROVED ─► PUBLISHING QUEUE ─► PUBLISHED   REJECTED
                                                       └──────► FAILED (retry ≤ 3)
                                                       └──────► MANUAL ACTION (API cannot publish;
                                                                  a person posts it and records the link)
```

1. **Discovery** (`lib/engine/discovery.ts`) asks each connected account's
   adapter for content using only documented endpoints (see
   `platform-capabilities.md`). Team members can also add a post by URL
   ("manual intake") for platforms whose API cannot search. Daily opportunity
   limits are enforced per client and per platform.
2. **Scoring** (`lib/engine/scoring.ts`) produces a 0–100 score from six
   weighted factors, a label ("Strong opportunity") and a plain-English
   explanation. The UI states that scores estimate relevance and do not
   guarantee engagement.
3. **Generation** (`lib/ai/generate.ts`) produces exactly three comments —
   insight, conversation, expert perspective — from post + author + brand +
   audience + campaign + previously approved/edited comments.
4. **Quality** (`lib/engine/quality.ts`) runs seven checks: relevance, spam,
   duplicate (embeddings, same client only), brand voice, promotional language,
   safety (incl. claims needing approval and fabricated personal experiences)
   and platform policy risk (length, links, mentions, hashtags). Any `fail`
   blocks bulk approval.
5. **Approval** follows the client's mode: `manual` (client approves),
   `gbs` (GBS account manager approves) or `dual` (both). A Postgres trigger
   refuses to mark a comment approved until the required sides have recorded
   approvals, refuses to queue an unapproved comment, and wipes earlier
   approvals if the text is edited.
6. **Publishing** (`lib/engine/publisher.ts`) claims jobs with
   `FOR UPDATE SKIP LOCKED`, re-checks approval, checks internal daily limits
   and per-account spacing, decrypts the token bound to *that* client and
   account, and calls the adapter. If the platform API has no endpoint for the
   action, the job becomes `manual_required` — the engine never falls back to
   scraping or browser automation.
7. **Tracking** pulls comment and profile metrics where the API exposes them.

There is **no automatic-approval mode**. "Auto publish" in this system only
means "an approved comment is published by the worker without a second click";
approval itself is always a human action, enforced in the database.

## 6. Security

| Requirement | Implementation |
| --- | --- |
| OAuth token encryption | AES-256-GCM (`TOKEN_ENCRYPTION_KEY`, 32 bytes). Additional authenticated data = `client_id:social_account_id`, so a ciphertext copied to another client's row fails to decrypt. Key version stored for rotation. |
| Server-side API calls | All platform and AI calls run in server actions, route handlers or the worker. Nothing secret is sent to the browser. |
| Role-based access | `lib/auth/permissions.ts` (UI/guards) mirrored by RLS helpers (enforcement). |
| Row Level Security | §4. |
| Secure cookies | `HttpOnly`, `Secure` (production), `SameSite=Lax`, opaque 256-bit token, only its SHA-256 stored. |
| CSRF | Server actions verify `Origin` against `Host`; route handlers that mutate check `Origin` too (`lib/security/csrf.ts`); OAuth uses a single-use, hashed `state` bound to the user and client. |
| Input validation | Zod schemas on every action and route. |
| Rate limiting | Postgres fixed-window limiter (`rate_limits`) for login, AI generation, discovery and publishing — works across instances. |
| Audit logs | `audit_logs`, append-only (trigger blocks `UPDATE`/`DELETE`). |
| Environment variables | `.env.example`; secrets are never prefixed `NEXT_PUBLIC_`. |
| Headers | CSP, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `X-Content-Type-Options`. |

## 7. Not a spam bot

The design rules out each prohibited behaviour structurally:

* Only official, documented APIs; capabilities an API lacks are declared
  `unsupported` or `manual` in the adapter and the engine respects them.
* No CAPTCHA solving, proxy rotation, credential collection, fake accounts or
  session reuse — there is no code path for any of these.
* Rate limits from the platform are honoured (back-off on 429 / quota errors);
  internal limits are additional, never a way around platform ones.
* Opportunities must clear a relevance score and quality checks; generic
  ("Great post!") and promotional ("DM us") comments are flagged.
* Approval is mandatory and enforced in the database.
* The generator is instructed never to invent personal experiences or
  misrepresent the client; the safety check flags first-person anecdotes.

## 9. White-label and SaaS readiness

* `organizations` is the tenant root; GBS is just the first organisation.
  `organizations.branding` holds `brand_name`, `logo_url`, `primary_color`,
  `email_sender`, `custom_domain`; the shell already reads name and colour from it.
* `usage_events` records AI generations, opportunities analysed, comments
  generated/published, API calls and account connections per client — the
  meter a billing system would read. `usage_limits` holds quotas.
* Authentication sits behind `lib/auth/session.ts`; replacing it with Supabase
  Auth / SSO means mapping the external identity to `users.id` and setting
  `app.user_id` — policies do not change.
